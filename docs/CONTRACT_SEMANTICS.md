# Contract Semantics

**Audience:** Contributors who need the unwritten rules — the behavioral invariants that every
contract must respect to interoperate correctly.

---

## 1. Cross-Contract Calls

### 1.1 Client Pattern

All inter-contract calls go through `#[contractclient]`-generated `Client` structs. Raw
`env.invoke_contract()` is never used in production code.

```rust
// remittance_split/src/lib.rs
#[contractimpl]
impl RemittanceSplitContract {
    pub fn get_split(env: Env) -> Vec<u32> { /* ... */ }
}
```

```rust
// orchestrator/src/lib.rs
#[contractclient(name = "RemittanceSplitClient")]
pub trait RemittanceSplitInterface {
    fn get_split(env: Env) -> Vec<u32>;
}

fn use_split(env: &Env, addr: &Address) -> Vec<u32> {
    let client = RemittanceSplitClient::new(env, addr);
    client.get_split()  // single-underscore namespace
}
```

**Key rules:**

- The trait method signatures must match the `#[contractimpl]` methods exactly (arg types, return
  type, whether `env` is by value or reference).
- A call through `Client` **panics** on the callee's error — there is no automatic `Result`
  propagation across contract boundaries. Use `try_` variants for fallible calls (see §1.2).
- The callee's `#[contracterror]` is **not** transmitted to the caller. The caller only sees
  `Ok(Val)` or a panic.

### 1.2 Try-Variant Fallback

When an orchestrator or coordinator needs to handle a downstream failure gracefully (e.g. skip a
bill payment that doesn't exist rather than aborting the entire remittance flow), it uses the
`try_` prefix that Soroban's contractclient macro generates automatically:

```rust
// orchestrator
let result = client.try_get_split();
match result {
    Ok(Ok(split)) => { /* use split */ }
    Ok(Err(_)) | Err(_) => {
        // downstream unavailable or panicked — degrade gracefully
        return Err(OrchestratorError::DependencyFailed);
    }
}
```

**Semantic contract:**

| Wrapper | Caller sees callee panic? | Caller sees callee `Err`? | Use case |
|---------|--------------------------|---------------------------|----------|
| `client.method()` | Panics | N/A | Caller wants hard failure on any callee error |
| `client.try_method()` | `Err(_)` | `Ok(Err(_))` | Caller wants to handle failures |

The `try_` wrapper is generated by the `#[contractclient]` macro for every method. There is no opt-out.

### 1.3 Compensation / Reversible Operations

When the orchestrator performs an atomic multi-step remittance flow and one step fails after
earlier steps have already committed, it runs **compensation** (rollback) operations on each
successful step, in reverse order.

Each contract that participates in orchestrated flows exposes a reversible interface:

```rust
// remitwise-common/src/reversible_op.rs
pub trait SavingsGoalsReversible {
    fn remove_from_goal(
        env: Env, user: Address, goal_id: u32, amount: i128,
    ) -> Result<bool, ReversibleOpError>;
}

pub trait BillPaymentsReversible {
    fn reverse_payment(
        env: Env, user: Address, bill_id: u32, amount: i128,
    ) -> Result<bool, ReversibleOpError>;
}
```

**Semantic contract for compensation:**

| Outcome | What happens |
|---------|-------------|
| Compensation succeeds | Operation is fully rolled back; orchestrator emits `flow_fail` event |
| Compensation returns `NothingToReverse` | Treated as success — nothing to undo (e.g. the step was a no-op) |
| Compensation fails (`NotFound`, `InvalidState`) | Orchestrator **still** considers the flow failed and propagates the compensation error; this is an invariant violation and should be investigated |

The `compensate_on_failure` flag in `run_remittance_fan_out` controls whether compensation runs.
When disabled, a partial failure leaves state partially committed (for manual resolution).

### 1.4 Reentrancy Guard

The orchestrator uses a reentrancy lock to prevent recursive invocations:

```rust
// orchestrator
const EXEC_LOCK: &str = "EXEC_LOCK";
struct LockGuard;  // Drop releases the lock
```

- The lock is stored as a boolean in instance storage.
- `LockGuard`'s `Drop` implementation clears the lock on scope exit, even if the call panics.
- All orchestrator entrypoints check the lock at entry and return `OrchestratorError::ReentrantCall`
  if already held.
- Contracts called by the orchestrator **must not** call back into the orchestrator.

## 2. Authorization

### 2.1 require_auth() Panics on Failure

`Address::require_auth()` panics when the caller is not authorized. It never returns `Err`. This
is Soroban SDK behaviour — the panic is caught by the host and surfaced as a failed transaction.

```rust
// Correct — panics on failure
fn write(env: Env, caller: Address) {
    caller.require_auth();
    // ...
}
```

```rust
// WRONG — require_auth does not return Result
fn write(env: Env, caller: Address) -> Result<(), MyError> {
    caller.require_auth()?;  // compile error
    Ok(())
}
```

Because `require_auth()` panics (it doesn't return `Err`), it cannot be used with `?`. The
function either continues (caller is authenticated) or the transaction fails immediately.

### 2.2 Role Verification

After `require_auth()`, every state-changing function performs an explicit role check against the
stored owner or admin address:

```rust
fn admin_only(env: Env, caller: Address) -> Result<(), Error> {
    caller.require_auth();
    let admin: Address = env.storage().instance()
        .get(&symbol_short!("ADMIN"))
        .ok_or(Error::NotInitialized)?;
    if caller != admin {
        return Err(Error::Unauthorized);
    }
    Ok(())
}
```

**Semantic contract:**

- `require_auth()` proves the caller controls the private key for that address.
- The contract then independently checks whether that address is permitted to perform the action.
- These two steps are never combined into a single check. The signature verification and the role
  authorization are separate concerns.

### 2.3 Upgrade Admin

Each contract stores a separate upgrade admin address (distinct from the owner/admin):

```rust
env.storage().instance().set(&symbol_short!("UPG_ADM"), &upgrade_admin);
```

An upgrade-protected entrypoint enforces caller == upgrade admin. This prevents the regular admin
from overwriting contract logic without the upgrade admin's consent.

## 3. Storage

### 3.1 Instance vs Persistent

| Storage tier | Typical use | TTL policy |
|---|---|---|
| `env.storage().instance()` | Contract config, owner, admin, counters, pause state | Extended via `bump_instance()` |
| `env.storage().persistent()` | Per-user records: goals, bills, policies, schedules | Extended via `bump_persistent()` for active records, `bump_archive()` for archived |

**Instance storage** cannot be deleted (no `remove` for individual keys). Use instance for data
that lives for the entire contract lifetime.

**Persistent storage** entries have individual TTLs. Every read of a persistent entry must be
followed by a TTL bump for the record to survive. The `remitwise-common` helpers encode consistent
thresholds:

```rust
fn bump_persistent(env: &Env, key: &DataKey) {
    env.storage().persistent().extend_ttl(key,
        INSTANCE_LIFETIME_THRESHOLD,  // 1 day
        PERSISTENT_BUMP_AMOUNT,       // 60 days
    );
}
```

**Semantic rule:** Every persistent read in a public entrypoint must call `bump_persistent`
(or equivalent) before returning, unless the entry is being deleted.

### 3.2 Key Naming

| Rule | Detail |
|---|---|
| Max length | 9 bytes (enforced by `symbol_short!`) |
| Character set | Uppercase ASCII + underscore (`A-Z`, `0-9`, `_`) |
| Convention | `UPPER_SNAKE_CASE` for `symbol_short!` keys |
| Multi-part keys | Use `#[contracttype]` enum with `DataKey` variants for complex schemas |

Examples:

```rust
// Short keys — symbol_short!
symbol_short!("CONFIG")
symbol_short!("OWNER")
symbol_short!("NEXT_ID")
symbol_short!("UPG_ADM")
symbol_short!("PAUSED")

// Complex keys — DataKey enum
#[contracttype]
pub enum DataKey {
    Policy(u32),
    OwnerPolicies(Address),
    ActivePolicies,
}
```

### 3.3 ID Allocation

Monotonic counters are stored in instance storage under `NEXT_*` keys:

```rust
let mut next_id: u32 = env.storage().instance()
    .get(&symbol_short!("NEXT_ID"))
    .unwrap_or(0);
let id = next_id;
next_id += 1;
env.storage().instance().set(&symbol_short!("NEXT_ID"), &next_id);
```

| Counter key | Contract | Used for |
|---|---|---|
| `NEXT_ID` | remittance_split, savings_goals, bill_payments, insurance | Primary entity IDs |
| `NEXT_RSCH` | bill_payments | Recurring schedule IDs |
| `NEXT_SSCH` | savings_goals | Savings schedule IDs |
| `NEXT_PSCH` | insurance | Premium schedule IDs |
| `NEXT_TX` | family_wallet | Transaction IDs |

IDs are never reused. A deleted/archived entity's ID is not reassigned.

## 4. Error Handling

### 4.1 Error Enums

Every contract defines a `#[contracterror]` enum with `#[repr(u32)]`:

```rust
#[contracterror]
#[repr(u32)]
pub enum BillPaymentsError {
    NotInitialized = 1,
    Unauthorized = 2,
    InvalidAmount = 3,
    BillNotFound = 4,
    AlreadyPaid = 5,
    // ...
}
```

**Semantic rules:**

| Rule | Reason |
|---|---|
| Discriminants start at 1 | `0` is ambiguous with `Ok(())`-like default values |
| Discriminants never change once deployed | Clients and indexers match on numeric codes |
| New variants append at the end | Inserting in the middle shifts downstream variant meaning |
| No gap reuse after deletion | Removed variants are marked as `_Reserved(u32)` if referenced externally |

The invariant tests in `remitwise-common` assert discriminant stability for shared error types.

### 4.2 Error Propagation Across Contracts

When contract A calls contract B via `Client`:

- If B panics (e.g. from `require_auth()` or `unwrap()`), the panic propagates to A's caller and
  the transaction fails. A cannot catch it.
- If B returns `Err(...)`, A receives `Ok(Err(...))` only when using `try_method()` (see §1.2).
  Direct calls (`client.method()`) panic on `Err`.
- B's error discriminant is **not** preserved across the call boundary. A only sees that B returned
  an error, not which error. Use `try_` + match for inspection.

### 4.3 Pre-Condition Checks

Public entrypoints validate pre-conditions before mutating state:

```rust
pub fn create_bill(env: Env, owner: Address, amount: i128, ...) -> Result<u32, BillPaymentsError> {
    owner.require_auth();
    if amount <= 0 { return Err(BillPaymentsError::InvalidAmount); }
    if name.len() == 0 { return Err(BillPaymentsError::InvalidName); }
    // ... mutations follow
}
```

**Semantic rule:** All `Err` returns must be triggered **before** any state mutation for that
call. Once storage is written, the function must commit (barring compensation — see §1.3).

## 5. Events

### 5.1 Dual Emission

Most state-changing operations emit two events:

```rust
// 1. Contract-specific event (namespace-prefixed topic)
env.events().publish(
    (symbol_short!("bill"), BillEvent::Created),
    (next_id, owner.clone(), external_ref.clone()),
);

// 2. Standardized event (RemitwiseEvents)
RemitwiseEvents::emit(
    &env,
    EventCategory::State,
    EventPriority::Medium,
    symbol_short!("created"),
    (next_id, owner, amount, due_date),
);
```

**Why both?**

| Layer | Consumer | Format stability |
|---|---|---|
| Contract-specific | Off-chain indexers tuned to this contract | Stable within the contract version |
| Standardized (`RemitwiseEvents`) | Cross-contract dashboards, aggregated feeds | Stable across the workspace |

### 5.2 Topic Structure

**Contract-specific events** have a two-part topic:

```
(namespace_symbol, event_variant)
```

Where `namespace_symbol` is `symbol_short!("bill")`, `symbol_short!("insure")`,
`symbol_short!("split")`, `symbol_short!("savings")`, etc.

**Contract-specific event variants** are `u32`-discriminated enums:

```rust
#[contracttype]
pub enum BillEvent {
    Created = 0,
    Paid = 1,
    // ...
}
```

**Standardized events** have a four-part topic:

```
(symbol_short!("Remitwise"), category_u32, priority_u32, action_symbol)
```

Where `action_symbol` is one of: `created`, `paid`, `cancelled`, `archive`, `restored`,
`paused_v2`, `unpaused_v2`, `init_ok`, `flow`, `flow_ok`, `flow_fail`, `snap_pre`, `snap_rst`.

### 5.3 Emission Timing

Events are emitted **after** the corresponding state mutation is persisted:

```rust
env.storage().instance().set(&key, &new_value);
env.events().publish(topic, data);
```

This guarantees that an indexer consuming the event in the same ledger close will see the updated
state. Reversing the order (event before write) would create a race window where the event refers
to stale state.

## 6. Initialization & Upgrade

### 6.1 One-Time Init

Every contract that requires setup has an `init` or `initialize_*` entrypoint guarded by a
storage key check:

```rust
pub fn init(env: Env, owner: Address) -> Result<(), Error> {
    if env.storage().instance().has(&symbol_short!("OWNER")) {
        return Err(Error::AlreadyInitialized);
    }
    env.storage().instance().set(&symbol_short!("OWNER"), &owner);
    Ok(())
}
```

**Semantic contract:**

| Condition | Behaviour |
|---|---|
| `init()` called before any `init()` | Succeeds, writes initial state |
| `init()` called a second time | Returns `Err(AlreadyInitialized)` |
| Non-init entrypoint called before `init()` | Returns `Err(NotInitialized)` |

The guard check is the first thing in `init()` and the first thing in every dependent entrypoint:

```rust
pub fn read_after_init(env: Env) -> Result<Config, Error> {
    let config = env.storage().instance()
        .get(&symbol_short!("CONFIG"))
        .ok_or(Error::NotInitialized)?;
    Ok(config)
}
```

### 6.2 Upgrade Lifecycle

Contract upgrades follow a three-phase pattern:

1. **`pre_upgrade(caller)`** — caller must match upgrade admin. Snapshots current state
   (`schema_version`, counters, upgrade admin, pause state) to persistent storage.
2. **`restore_from_snapshot(caller)`** — validates the stored `schema_version` matches the new
   contract version expectation, then restores counters and admin addresses.
3. **`discard_snapshot(caller)`** — removes the snapshot without restoring (abort the upgrade).

**Semantic rules:**

- `pre_upgrade` and `restore_from_snapshot` / `discard_snapshot` are always paired. A dangling
  snapshot blocks sensitive operations (e.g. another `pre_upgrade`).
- `schema_version` is hard-coded in the new WASM binary and compared against the snapshot's
  stored version. Mismatch = reject.
- The upgrade admin is distinct from the regular admin to prevent unilateral upgrades.

## 7. Pagination

All paginated reads use cursor-based pagination:

```rust
pub fn get_bills(
    env: Env, owner: Address, cursor: u32, limit: u32,
) -> BillPage {
    let limit = clamp_limit(limit);
    let bills: Vec<Bill> = /* fetch from persistent storage */;
    let total = bills.len();
    let start = cursor.min(total);
    let end = (start + limit as usize).min(total);
    let page: Vec<Bill> = bills.slice(start..end);
    BillPage {
        bills: page,
        next: if end < total { end as u32 } else { 0 },
    }
}
```

**Semantic rules:**

| Property | Guarantee |
|---|---|
| `cursor == 0` | Start from the beginning |
| `next == 0` | End of results — no more pages |
| `cursor > total` | Empty page, `next == 0` |
| `limit` | Clamped to `MAX_PAGE_LIMIT` via `clamp_limit()` |
| Ordering | Oldest-to-newest within current state |
| Stability | Cursor is a position in a snapshot, not an immutable global ID. Concurrent writes between pages may shift results. |

## 8. Pause Semantics

### 8.1 Three-Level Pause

The `emergency_killswitch` and individual contracts implement a three-level pause hierarchy:

| Level | Key | Scope |
|---|---|---|
| Global | `PAUSED` | Entire contract frozen |
| Module | `PAUSED_FN` (module prefix) | Function group frozen |
| Function | `PAUSED_FN` (full key) | Single entrypoint frozen |

A function is executable only when **none** of the three levels are paused for that function.

### 8.2 Timed Unpause

The `UNP_AT` key stores a ledger timestamp. When set, the contract auto-unpauses on the next call
after that timestamp:

```rust
if let Some(unp_at) = env.storage().instance().get::<_, u64>(&symbol_short!("UNP_AT")) {
    if env.ledger().timestamp() >= unp_at {
        env.storage().instance().remove(&symbol_short!("UNP_AT"));
        env.storage().instance().remove(&symbol_short!("PAUSED"));
    }
}
```

This is an automatic recovery mechanism — a timed pause expires without operator intervention.

## 9. no_std Compilation Discipline

All contract crates compile with `#![no_std]` for the WASM target. This means:

| Allowed | Not allowed |
|---|---|
| `soroban_sdk::Vec`, `soroban_sdk::Map`, `soroban_sdk::Bytes` | `std::vec::Vec`, `std::collections::HashMap` |
| `soroban_sdk::Symbol::new()` | `String`, `format!()` |
| `core::result::Result`, `core::option::Option` | `std::error::Error`, `std::io` |
| `#[cfg(test)]` modules (may use `std`) | `std` in non-test code |

The Cargo.toml `release` profile uses `panic = "abort"`, which means `catch_unwind` and similar
panic-catching mechanisms do not work.

## 10. Sanity Checklist for Contributors

Before opening a PR, verify these semantic rules:

- [ ] `require_auth()` is called **before** authorization role checks and state mutations
- [ ] All `Err` returns happen **before** the first state write in that call
- [ ] Persistent storage reads bump TTL before returning
- [ ] Event emissions use the dual pattern when the operation is externally visible
- [ ] Error discriminant codes are unique and start at 1
- [ ] Cross-contract calls use `Client::new(&env, &addr)` — no raw `invoke_contract`
- [ ] `try_` variants handle downstream failure gracefully when the caller tolerates it
- [ ] ID counters use saturating increment and start at 0
- [ ] Init guards check for duplicate initialization
- [ ] `#![no_std]` is not used in non-crate-root files (e.g. utils.rs in reporting)
- [ ] `clamp_limit()` wraps every paginated `limit` parameter
- [ ] Unescape/expect are gated behind `#[cfg(not(test))]` bans (see `deny.toml`)
