# Upgrade Testing with a Previous Snapshot

This guide is for **contributors** changing a contract's persisted data, a
snapshot schema, or snapshot-validation code. Its purpose is to prove that the
new code can load data produced before the change and still enforces the
invariants that protect live state.

Use this procedure before merging an upgrade that can read an existing
snapshot. It complements the operator-focused [Contract Upgrade
Runbook](UPGRADE_RUNBOOK.md); it does not describe how to execute a live
upgrade.

## The procedure

1. Obtain a snapshot generated by the revision immediately before the change.
   Keep the original bytes unchanged and record the source revision, export
   format, and checksum with the test fixture. Do not regenerate the fixture
   with the new code: that would only prove that the new exporter and importer
   agree with each other.
2. Load those original bytes through the normal tracked import entrypoint:
   `data_migration::import_from_binary` for binary snapshots or
   `data_migration::import_from_json` for JSON snapshots. Pass a persistent
   `MigrationTracker`; the tracked functions reject a second import of the same
   `(checksum, version)` identity.
3. Require the load to succeed, then assert the business invariants for that
   payload. A successful decode or checksum check alone is not sufficient.
4. Run the affected contract's snapshot import test as well. Contract imports
   add contract-specific authorization, nonce, pause, and storage checks that
   the off-chain migration crate cannot perform.

## Concrete binary-snapshot check

The following is the pattern used by the migration crate. `import_from_binary`
performs the compatibility, size, hash-algorithm, checksum, and semantic
validation before it returns a snapshot.

```rust
use data_migration::{import_from_binary, MigrationError, MigrationTracker};

fn load_previous_snapshot(previous_release_bytes: &[u8]) -> Result<(), MigrationError> {
let mut tracker = MigrationTracker::new();
let snapshot = import_from_binary(previous_release_bytes, &mut tracker, 1_000)?;

assert!(snapshot.verify_checksum());
snapshot.validate_for_import()
}
```

For an upgrade test, `previous_release_bytes` must come from the pre-change
release fixture, not from a call to `export_to_binary` in the same test. Keep
the tracker alive for the test when replay protection is part of the expected
behaviour.

## Invariants to verify

`ExportSnapshot::validate_for_import` verifies the generic snapshot boundary:

- the version is within the supported range;
- record count and payload size are bounded;
- the hash algorithm is recognized and the checksum matches; and
- payload-specific semantic invariants hold.

The current payload invariants are:

| Payload | Required invariant after loading |
| --- | --- |
| `RemittanceSplit` | Every percentage is at most 100 and all four percentages sum to exactly 100. |
| `SavingsGoals` | `next_id` is at least the highest goal ID, and each `current_amount` is no greater than `target_amount`. |
| `Generic` | No additional business invariant beyond the generic validation boundary. |

When an upgrade adds a field or changes a contract-level rule, add assertions
for that rule alongside the previous-snapshot test. For example, a remittance
split upgrade must confirm that the loaded allocation still totals 100 before
it is handed to the contract import path.

## Required commands

Run the migration checks against the preserved snapshot, then run the standard
workspace gates from the repository root:

```bash
cargo test -p data_migration
cargo build --target wasm32-unknown-unknown --release
cargo clippy --workspace --all-targets -- -D warnings
```

If the snapshot belongs to a contract-specific export/import API, also run that
crate's tests, for example:

```bash
cargo test -p remittance_split
```

## Failure handling

Treat a previous snapshot that cannot be loaded or violates an invariant as an
upgrade compatibility failure. Do not update its checksum, serialize it again,
or weaken validation merely to make the test pass. Either supply an explicit,
reviewed migration path or retain compatibility with the prior snapshot format.

format stability](binary-format-stability.md), and the [Contract Upgrade
